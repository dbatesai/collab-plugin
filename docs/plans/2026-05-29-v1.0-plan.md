## §0 — One-line summary

collab-plugin v1.0 makes multi-agent collaboration reliable enough to use without babysitting: base loop works flawlessly on both harnesses, dynamic cadencing approaches pub/sub feel over a polling substrate, typed status payloads make progress observable, and preflight gates catch problems before they start. Everything earned, nothing theatrical.

## §1 — Scope

**In scope:**

1. `collab-loop` command: `start`, `status`, `stop` with durable cursor state
2. Dynamic cadencing: adaptive polling with fast-poll window + ladder-up-on-idle
3. Typed status block protocol: State/Owner/Last-action/Waiting-on/Next-action/Next-check/Risk
4. Typed event payload validation: reject malformed payloads at tick time, not silently
5. Per-participant obligation tracking + chase emission (binds GH#2)
6. Transport preflight + capability check before kickoff (binds GH#3)
7. Provenance stamp on every v1 emitter, ALL harnesses (HK and HC side; binds GH#3)
8. Version detection fix: fall back to path-based detection when env vars absent
9. Shared-state ownership semantics: no implicit "peek at peer memory"
10. Multi-agent earns-its-keep gate at kickoff

**Deferred to v1.1+:**
- Multi-project contract inheritance
- Cross-machine authentication tokens
- Participant health scoring / trust levels
- UI or dashboard

**Non-goals:**
- "Digital department" theater: large agent pools, broad coordinators
- Replacing CORE's adversarial protocol machinery (v2.8.0/v2.9.0 scope)
- Same-session (intra-harness) orchestration: Dynamic Workflows handles that

## §2 — Design principles (from HC Reddit research)

These shape every feature decision:

1. **Code owns control flow; agents own ambiguity.** Cadence ladder, deadline checks, stale-agent detection, close/ratify rules, progress summaries = deterministic code. LLM reasoning = only where judgment is unavoidable.

2. **Multi-agent earns its keep.** Kickoff requires a `justification` field naming the genuine parallelism, role separation, or adversarial value. A kickoff that can't articulate this is refused.

3. **Handoffs are typed API contracts.** Every event that transfers ownership carries `owner`, `waiting_on`, `next_update_by`, `state` (working/blocked/verifying/done) as required fields. Invalid payloads rejected at tick time.

4. **Shared mutable state needs explicit ownership.** No implicit peer memory reads. If HK needs HC's decision, it must be serialized into a referenced event. If two participants can write the same surface, require explicit lock/claim or deterministic conflict resolution.

5. **Observability as protocol output.** `collab-loop status` renders the typed status block. Users should know who owns what, what's blocked, and when to expect the next update — from the system, not from reading agent prose.

6. **Chase the agent, not the harness.** Obligation tracking per-participant with absolute deadlines. A missed `next_update_by` triggers a chase event with the participant's name, not a generic timeout.

7. **Boundary evals before pub/sub.** Dynamic cadencing ships only after base-loop reliability is confirmed: every boundary (kickoff, turn, propose-close, ratify, safety-net) has a regression test.

## §3 — collab-loop command

### §3.1 — `collab-loop start <slug>`

```
collab-loop start <slug> [--fast-poll-minutes N] [--base-cadence-minutes N]
```

Joins the collab in loop mode:
1. Validates minimum version (fix: path-based fallback when env vars absent)
2. Runs preflight check (§6)
3. Reads or initializes cursor state from the identity-rich path `~/.collab/cursors/<machine-slug>/<harness>/<participant-encoded-triplet>-<slug>.json` (see §3.1 schema)
4. Enters the tick loop with configured cadence

Cursor file path: `~/.collab/cursors/<machine-slug>/<harness>/<participant-encoded-triplet>-<slug>.json`
- `machine-slug` = output of `hostname -s`
- `harness` = `claude-code` | `codex` | `gemini`
- `participant-encoded-triplet` = triplet with `@` and `:` replaced by `-`
- Example: `~/.collab/cursors/jennifer-aniston/claude-code/core-framework-claude-code-jennifer-aniston-keel-hk-here-starting.json`

Cursor state schema:
```json
{
  "slug": "string",
  "transport": "github:files | localhost",
  "participant_triplet": "string",
  "machine": "string",
  "harness": "string",
  "last_seen_event_id": "string | null",
  "last_posted_at": "ISO timestamp | null",
  "fast_poll_window_expires_at": "ISO timestamp | null",
  "base_cadence_minutes": 5,
  "fast_poll_minutes": 0.5,
  "last_committed_next_update_by": "ISO timestamp | null",
  "commitment_drift_state": "on-time | late | missed | unknown"
}
```

### §3.2 — `collab-loop status <slug>`

```
collab-loop status <slug>
```

Renders the typed status block for the collab:
```
State: [working|blocked|verifying|done]
Owner: <participant>
Last action: [prose from last event]
Waiting on: [participant or "nothing"]
Next action: [prose]
Next check: [timestamp from next_update_by]
Risk: [prose]
Stall: [N minutes since last event / stall limit]
```

Also shows:
- Current cadence mode: fast-poll (N min) vs base (N min)
- All participant obligation deadlines
- Events since cursor (count + list of IDs)

### §3.3 — `collab-loop stop <slug>`

```
collab-loop stop <slug>
```

Saves cursor state to disk. Loop can be resumed by re-running `start`. Does NOT close the collab.

## §4 — Dynamic cadencing

### §4.1 — Cadence ladder

**Three states:**

| State | Interval | Trigger |
|-------|----------|---------|
| Fast-poll | 30 seconds | After posting an event OR receiving a new event |
| Base | 5 minutes | Fast-poll window expires (5 min after last activity) |
| Idle | 15 minutes | No event from any participant for > 30 minutes |

**Coordination via `next_update_by`:** When posting an event, include `next_update_by` in the payload. The receiving agent's tick loop reads this field and will not chase before that timestamp.

**Fast-poll window logic (deterministic, in collab-cadence.mjs):**
```
on post_event:
  cursor.fast_poll_window_expires_at = now() + 5 minutes
  cursor.save()

on new_event_received:
  cursor.fast_poll_window_expires_at = now() + 5 minutes
  cursor.save()

on_tick:
  if cursor.fast_poll_window_expires_at > now():
    sleep 30s
  else if time_since_last_any_event > 30min:
    sleep 15min
  else:
    sleep 5min
```

### §4.2 — What this achieves

If both participants cooperate (both use fast-poll windows):
- Agent A posts → fast-poll mode for 5 min (checks every 30s)
- Agent B sees event within 30s → fast-poll mode → responds → A sees within 30s
- Effective round-trip latency: ~60s at worst

If one participant is slow:
- Fast-poll expires after 5 min → ladder up to base cadence
- No wasted constant-high-frequency polling when nothing is happening

### §4.3 — Constraints

- Hard floor: 30 seconds. Never poll faster.
- Hard ceiling: 30 minutes. Never go slower (safety nets need this).
- Dynamic Workflows can replace the loop machinery for same-session use. Cross-machine always uses the file-based tick.

## §5 — Typed event payload validation

### §5.1 — Required fields for `turn` events

```typescript
type TurnPayload = {
  intent: "propose" | "critique" | "synthesize" | "probe" | "clarify";
  body: string;                  // substantive content (not heartbeat)
  state: "working" | "blocked" | "verifying" | "done";
  owner: string;                 // participant triplet that owns next action
  waiting_on: string | null;     // participant or null
  next_update_by: ISO8601String; // required; empty string = no deadline
};
```

### §5.2 — Validation at tick time (quarantine model)

`collab-tick.mjs` validates payload fields before routing. For v1 events:
- Missing `state`, `owner`, or `next_update_by` → **quarantine** the event (write to `events/.quarantined-<id>.json` with `quarantine_reason`; do NOT process in tick routing). Chase logic does not trigger against quarantined events.
- Missing `provenance.emit_mode` on v1+ events → quarantine with `missing-provenance`
- `body` that looks like a heartbeat (< 20 words, no code/plan/decision) → warn only (not quarantine — body quality is advisory)
- Missing `references` when clearly responding to a prior event → warn only

For v0.2 legacy events (no `schema_version` field): warn only on any missing fields; do not quarantine (backwards compatibility).

### §5.3 — Boundary eval suite

`tests/scripts/collab-payload-validation.test.mjs` — covers all rejection/warning cases:
1. v1 event missing `state` field → QUARANTINE (per §5.2), not processed in tick routing
2. v1 event missing `owner` or `next_update_by` → QUARANTINE
3. v0.2 legacy event missing fields → warning only (no quarantine)
4. `next_update_by` in the past → chase escalation trigger
5. `owner` pointing at non-participant → warning
6. `body` under 20 words → heartbeat warning
7. `references` missing on evident reply → warning

## §6 — Transport preflight (binds GH#3)

### §6.1 — What it checks before kickoff (six-point list)

For `github:files` transport, all six must pass:

1. **Entrypoint resolution**: script path resolves to the expected collab plugin (not a stale symlink or wrong version)
2. **Plugin version**: installed plugin version ≥ minimum required (using path-based fallback when env vars absent)
3. **Route dry-run**: validateMutationProfile on required capability rows — confirm the pre-action profile would permit the kickoff write
4. **Local write test**: write and delete a temp file in the collab directory to confirm filesystem access
5. **Pull/rebase**: `git pull --rebase` succeeds (no diverged commits that would block push)
6. **Push dry-run**: `git push --dry-run` succeeds OR emits explicit warning that push may fail (does not hard-block; logs finding)

Plus these apply to all transports:
- Slug unique across known transports
- Kickoff message includes `justification` field (the "earns its keep" gate)

### §6.2 — Provenance stamp (binds GH#3)

Every v1 event emitted by `appendEvent` includes a provenance envelope:
```json
{
  "provenance": {
    "emit_mode": "interactive | supervised | automated",
    "harness": "claude-code | codex | gemini",
    "machine": "<hostname>",
    "install_source": "cache-path | env-var | unknown",
    "plugin_version": "1.0.0",
    "tool_chain": "claude-code@4.8 | codex@0.133 | unknown",
    "posted_at_local_time": "2026-05-29 12:00:00 AM EDT"
  }
}
```

For v1+ emitters: `provenance` is REQUIRED. Missing provenance → event is quarantined with `missing-provenance` reason. For legacy v0.2 events (pre-v1): provenance absent is allowed and warned only.

## §7 — Per-participant obligation tracking (binds GH#2)

### §7.1 — How it works

After each event, `collab-tick.mjs` computes the next-update obligation for each joined participant using the **issue #2 drift fields**:

Per-participant state (maintained in cursor file and STATUS.md):
- `last_committed_next_update_by`: most recent `next_update_by` from that participant's events
- `last_actual_update_at`: timestamp of their most recent `turn` event
- `commitment_drift_seconds`: `(last_actual_update_at or now) - last_committed_next_update_by`
- `commitment_drift_state`: `on-time | late | missed`

Tick logic:
- Read the most recent `turn` event per participant
- Extract `next_update_by` from payload's SCHEMA FIELD (not body text parsing)
- Update per-participant drift fields in cursor state
- If `now() > next_update_by + grace_period AND commitment_drift_state == 'missed'`: emit a chase event

Chase event has type `turn` with:
- `intent: "clarify"` 
- `body`: rendered in 12-hour local system time with timezone: "Obligation missed: <participant> expected update by <local-time>. Drift: <N> min. Current state unknown."
- `payload.state`: "blocked"
- `payload.owner`: <the overdue participant>
- `signals: ["chase", "obligation-missed", "<participant-triplet>"]`

This replaces manual chase discipline with deterministic code. Drift tracking is per-participant, per-collab. STATUS.md rendering surfaces obligation state for all participants.

### §7.2 — Grace period

Default 5 minutes. Configurable per-collab in kickoff payload. No grace period = immediate chase on deadline miss.

## §8 — Version detection fix

`readLocalPluginVersion()` in `collab-event-helpers.mjs` currently returns `0.0.0` when env vars are absent (which they are in Bash tool context — not just hooks).

Fix 1: add path-based fallback that returns version with `confidence` and `source` metadata:
```javascript
// EXISTING: env var chain (confidence: high, source: env-var)
// NEW fallback: extract version from install cache path
// e.g., ~/.claude/plugins/cache/collab/collab/0.2.0/skills/collab/scripts/...
const selfPath = fileURLToPath(import.meta.url);
const match = selfPath.match(/\/plugins\/cache\/[^/]+\/[^/]+\/(\d+\.\d+\.\d+)\//);
if (match) return { version: match[1], confidence: 'medium', source: 'cache-path' };
return { version: '0.0.0', confidence: 'none', source: 'fallback' };
```

Fix 2: `checkMinVersion()` accepts both `{ version, ... }` objects and plain string versions for backwards compat.

The version string form remains valid for callers that don't need confidence metadata. The `{ version, confidence, source }` form is for the capability row's provenance reporting.

## §9 — Multi-agent earns-its-keep gate

Kickoff payload requires:
```json
{
  "justification": {
    "reason": "adversarial-review | parallelism | role-separation | context-isolation | blast-radius",
    "explanation": "one sentence"
  }
}
```

For NEW multi-agent collabs (> 1 participant): `justification.reason` is REQUIRED. Absent or invalid reason → `collab-loop start` HARD REFUSES with clear error. No warning fallback.

For legacy `/collab` kickoff (v0.2 compatibility path): missing justification emits a warning but does not block. `/collab` users are on the legacy path until they upgrade to `collab-loop start`.

This makes the "why are we using multi-agent?" explicit and queryable.

## §12 — Settled decisions + remaining open questions

**Settled (consensus reached with HC):**
- `justification` gate: `collab-loop start` HARD-REFUSES absent justification for new multi-agent collabs; legacy `/collab` warns. Settled (§9).
- Provenance: REQUIRED for v1+ emitters, quarantined if absent; legacy v0.2 warned only. Settled (§6.2).

**Remaining open question (one, genuinely open):**
1. **Chase grace period default: 5 minutes or longer?** If shorter, every slow agent gets chase-spammed. If longer, the "pub/sub feel" degrades because missed deadlines aren't caught quickly. Recommendation: 5 minutes default, configurable per-collab. To confirm with HC during implementation.

**Version detection robustness note (not a blocker):** The path-based regex assumes the `/plugins/cache/<scope>/<name>/<version>/` layout. If that layout changes, detection returns `confidence: none`. A future hardening option is a `VERSION` file at plugin root, deferred to v1.1 (requires all installs to carry the file).

## §15 — Risks

- **Codex harness compatibility** — cadence state (cursor file) writes must work on Codex's filesystem. Test explicitly before claiming cross-harness PASS.
- **Fast-poll CPU overhead** — 30s polling × 2+ participants = 4+ reads/min per collab. With many collabs, this could be noisy. Mitigation: git pull only on tick; no filesystem watch.
- **Chase event flood** — if an agent is stuck (usage limit, long tool run), chase events accumulate. Mitigation: limit chase events to 3 per participant per wall-clock hour.
